## How to Use

This skill produces a **starter draft** of three conversation scenarios — a working set the team expands from, not a complete conversation design. The team or an Agentic Experience Specialist (AXS) extends this draft into corpus-grade design work afterwards: rewriting voice, adding error coverage, designing fallbacks at scale, deciding refusal points, calibrating clarification patterns. The skill is a **head start**, not a deliverable.

**What it produces (every run):**

- **Three scenarios** — exactly one of each `type`:
  - **Happy path** — the priority capability working end-to-end, no errors
  - **Error state** — a system or user error encountered during a flow (timeout, auth failure, invalid input, capability not yet built)
  - **Fallback** — a path the agent can't complete (out of scope, escalation, deferred capability, deadend) and how it exits gracefully
- **4–8 turns per scenario** — capped. Anything longer either belongs in two scenarios or wasn't ready to be designed at this fidelity yet.
- **`draft: true`**<b> flag on each scenario</b> — drives a top-of-page banner reminding readers it's a starter draft. The page renders only the role + utterance per turn; data fields below are recorded for future tools but not displayed.
- **`actions[]`**<b> per turn</b> — populated **only when** `_local/data/actions.yaml` exists from the architecture skill. Otherwise empty; the skill does not fabricate action IDs.
- **`components[]`**<b> per turn</b> — populated **only when** a visual upstream exists: `_local/data/concept-design.md` OR an existing `_local/data/style-guide.json` with components defined. Otherwise empty; the skill does not fabricate `style_ref` slugs against a vocabulary that may not match the engagement's surface decisions.
- **`prosody_cues[]`**<b> per turn</b> — populated only when channel is `voice` or `multimodal`. A small canonical set of cue types is acceptable here because prosody is channel-intrinsic; the persona doc grounds the markers.
- **`voice`**<b> bundle (voice / multimodal channels only)</b> — a 5-layer voice-UX rewrite (Instructions / Copy / Phrasebook / Opening / Handoff notes) plus an audit citing each change to a voice UX principle. Generated by Step 9.5 via vendored `voice-ux/` (skipped if `agentforce-generate` is not installed; the page renders an explainer in that case). Renders as a fourth `Voice` tab on the Conversation Design page.

<b>Why the </b>**`actions`**<b> / </b>**`components`**<b> arrays gate strictly.</b> Earlier versions of this skill wrote those fields against a baked-in canonical vocabulary regardless of upstream. That created chips on the page that pointed at action IDs and component slugs the engagement might not actually have — false signals. The renderer no longer displays them, but the data write itself should also be honest: if the upstream isn't there, the field is empty.

**Modes:**

- **Hub mode** — invoked from inside an AXS engagement. Detected by finding `project.config.json` in cwd or a parent. Reads engagement context (channel, persona, capability cut, architecture if present, transcript insights if present, concept design / style guide if present). Writes canonical state to `_local/data/conversation-design.json`. Returns control to the hub for publish.
- **Standalone mode** — runs from any folder. Requires at minimum a capability list. Produces `conversation-design.json` plus a markdown export.

**What it produces (both modes):**

- `_local/data/conversation-design.json` — single canonical file (see [Output Schema](#output-schema))

**What it produces (standalone only, additive):**

- `_local/exports/conversation-design.md` — customer-clean markdown export

**What it feeds downstream:**

- **Style Guide** — reads any `style_ref` slugs in this skill's output and resolves them into per-component specs. (Slugs are only present when this skill ran with a visual upstream; otherwise the Style Guide pulls from Concept Design directly.)
- **User Testing** — a flow-research session can run against these scenarios as the design-under-test. The Plan phase reads scenario titles and goals; the Findings phase routes recommended changes back here via `reviewFlag`.
- **Build-map / coverage tools (future)** — the `actions[]` field becomes load-bearing once those tools land. Honest empty arrays are better than fabricated action IDs.
- **The team's full conversation design pass** — corpus-grade design work picks up from this draft.

## When in the journey

Conversation Design unlocks once the capability cut is accepted (`capabilities.yaml` exists). Persona is a soft input — voice is much sharper when persona is in place; running without it produces flows in a generic agent voice that need a voice pass once persona lands.

This skill targets the **early-fidelity** moment specifically — three scenarios before the AXS staffs in, not the full conversation design after they do. The output is a *brief*, not a deliverable.

The skill captures which moment it ran in via `phase: design-fidelity | concept-fidelity`:

- **`design-fidelity`** *(default)* — full design fidelity: persona + capability cut + (optionally) architecture in place. The scenarios are fairly concrete; the limited preview is the right phase for them.
- **`concept-fidelity`** — earlier moment: only persona + use case + capability sketch are available. The scenarios are looser — closer to concept narratives than designed flows. Use when an AXS pass is far off and the team needs to feel the agent's shape before committing.

Pre-launch / post-build flows are out of scope here — that's regression testing, not design.

## AXS-led work gate (runs first, every invocation)

Conversation Design is craft work. Tone, pacing, refusal points, error voice, fallback language, handoff triggers — these are decisions a model can draft but can't decide for the team. **An Agentic Experience Specialist (AXS) leads the full pass when staffed; this skill produces a starter draft the team or AXS expands from.**

The hub's existing AXS-led work gate runs first when this skill is invoked. The three-way routing:

| User picks | Action |
| --- | --- |
| 1. Request AXS support *(recommended)* | Open `#axs-team-hub-skill`, mark `sections.conversation-design.axsStaffingRequested: true`. Don't run the skill. |
| 2. Generate a limited preview | Run the skill below. The output is *three scenarios* — strictly bounded. Mark `sections.conversation-design.limitedPreview: true`; section status = `in-progress`. The page surfaces a top-of-page draft banner until the team flips the per-scenario `draft` flags. |
| 3. Skip for now | Acknowledge, return to Resume Flow menu. No state changes. |

If the user explicitly invokes this skill (`/conversation-design`), they've effectively chosen option 2. The gate still runs — surface the limited-preview framing one final time before drafting:

> "Heads-up: this skill writes a **three-scenario starter draft** — one happy path, one error state, one fallback. It's a working set the team (or an AXS, if one is staffed) expands from, not the full conversation design. The full design pass adds error coverage across the corpus, rewrites voice, defines fallbacks at scale, calibrates clarification, and decides refusal points. Want me to continue with the starter draft, or request AXS support via `#axs-team-hub-skill` first?"

If the user confirms, proceed. If they switch to AXS support, mark `axsStaffingRequested: true` and exit cleanly.

## Entry Point Detection

```bash
# Look for project.config.json in cwd or up to 3 parents.
node -e '
const fs = require("fs");
const path = require("path");
let dir = process.cwd();
for (let i = 0; i < 4; i++) {
  if (fs.existsSync(path.join(dir, "project.config.json"))) {
    console.log("hub:" + dir);
    process.exit(0);
  }
  const parent = path.dirname(dir);
  if (parent === dir) break;
  dir = parent;
}
console.log("standalone");
'
```

- **`hub:<engagement-root>`** → **Hub mode**.
- **`standalone`** → **Standalone mode**.

**Override.** If the user explicitly says *"standalone mode"*, honour that even inside an engagement folder.

**Re-run detection.** After mode detection, check whether `_local/data/conversation-design.json` exists:

- File missing → first run. Proceed.
- File present, all scenarios `draft: true` → re-run prompt: <i>"Three draft scenarios are on file from \[drafted\_at\]. What would you like to do? 1. </i>***Refine***<i> the existing scenarios · 2. </i>***Replace***<i> with a fresh draft (archives the existing) · 3. </i>***Add a fourth scenario***<i> (the AXS pass usually expands; the skill keeps the three-per-run cap, so this archives the oldest and adds new) · 4. </i>***Show me what's there first****."*
- File present with at least one scenario marked `draft: false` → an AXS has shipped some flows. **Do not overwrite.** Tell the user: <i>"At least one scenario has been shipped by the AXS — I won't overwrite. The AXS owns this section now. To make changes, talk to them via </i>*`#axs-team-hub-skill`**, or pick a specific draft scenario to refine and I'll keep the shipped ones intact."*

## Prerequisite Check

Conversation design without a finalised capability list is wasted work. Before any other step, check for `capabilities.yaml`:

- **Hub mode**: read `<engagement-root>/_local/data/capabilities.yaml`. If absent, tell the user: <i>"Conversation design needs a capability cut to design against. Share the prioritised capabilities (a list or </i>*`capabilities.yaml`**) and I'll continue."* Stop the flow.
- **Standalone mode**: look for `./capabilities.yaml` or `./_local/data/capabilities.yaml`. If absent, ask the user to point at one. Don't proceed without it.

If the capability list has `signoff.status: pending`, warn but proceed: *"Capabilities are written but not signed off. I'll draft scenarios against the current cut — if it changes after sign-off, re-run the skill to refresh."*

## Interaction Design

**One scenario at a time.** Draft → preview → confirm → next. Don't dump three scenarios at once; the user can't review them in parallel.

**Surface picks before drafting.** Capability for happy path, error subtype, fallback subtype — each surfaced as a recommendation with rationale, user can override. Don't ask blind ("what scenario should I draft?"); make the picks explicit.

**Cap output strictly.** When the user pushes for more — second happy path, more turns, more error coverage — point at the cap and explain *why*: this is a starter draft, not a substitute for the full design pass. The cap keeps the artefact honest about its scope.

**Be transparent about gating.** When `actions.yaml` is missing or the visual upstream is absent, say so out loud during the run — *"I'll leave actions / components empty because architecture / Concept Design hasn't run yet"* — and surface the same info in `global_notes`. Silent empty fields are confusing; explicit empty fields with a reason are useful.

**Don't fabricate persona signals.** Generic-friendly voice with a flag is better than confident persona voice that the team rewrites from scratch.

**Don't fabricate action IDs.** If a turn implies an action that isn't in `actions.yaml`, leave the field empty and add to scenario `notes` (e.g. <i>"Turn 5 implies a </i>*`bill_breakdown`*<i> action that isn't in the architecture yet — flag for an architecture re-pass."</i>).

**Don't fabricate component slugs.** Components reference Concept Design's vocabulary or the Style Guide's slugs; without those upstream files, leave `components[]` empty.

**Don't fabricate prosody patterns for voice.** Default to a small set of conservative cues; the team layers in subtler patterns.

**Re-runs are first-class.** The skill is designed to be re-invoked — refine an existing scenario, replace one type, archive and start fresh. Don't treat re-run as an exception path.
